<div class="legacy-html" set:html={"<h2>Microsoft Fabric Medallion Architecture: Lessons Learned</h2><div class=\"divider\"></div><p class=\"paragraph-14\"><em>A practical account of migrating an older data platform to a Fabric medallion architecture – what we used to work with, why it had to change and how we built it better this time.</em></p><p class=\"paragraph-14\"><br/>Microsoft Fabric changed the way we build data platforms on top of Power BI. Before Fabric, the typical journey was straightforward: connect to a data source, load it into a semantic model, build your reports. Power Query for transformations, DAX for measures, done.</p><p class=\"paragraph-14\">Fabric introduced a new layer between the data and the report, and with it, a completely different set of tools and concepts. Lakehouses. Warehouses. Notebooks. Pipelines. Semantic models that connect to Delta tables instead of imported datasets. Suddenly, building a good Power BI solution wasn&#x27;t just about DAX and data modelling anymore. It was about understanding where data lives, how it moves and who processes it before it ever reaches a visual.</p><p class=\"paragraph-14\">We encountered this shift on a real project: an older data platform built in Microsoft Fabric, serving internal teams and external clients through Power BI reports. When the project was young, we built what made sense. When the project grew, we started feeling the ceiling. This is the story of what we built, what we outgrew and how we redesigned it without throwing away what was already working.</p><h3 class=\"heading-16\">The decision | What we wanted to achieve</h3><p class=\"paragraph-14\">We wanted to connect the semantic model via Direct Lake for live data without scheduled refreshes. We wanted fewer transformation layers, so there was a single place where business logic lived and could be tested. We wanted to support Power BI Embedded properly, which meant tighter control over environments and deployments. And we wanted the platform to scale (more data sources, more reports, more users) without the complexity compounding every time something new was added.</p><p class=\"paragraph-14\">Once those goals were on the table, the architecture almost designed itself. To get Direct Lake, you need Delta tables in OneLake. To get Delta tables that are clean and validated, you need a transformation layer that runs before data reaches the model. To get that transformation layer under control, you need a clear boundary between raw ingestion and processed data. That&#x27;s the medallion pattern: <strong>Bronze</strong> for raw, <strong>Silver</strong> for processed, <strong>Gold</strong> for the semantic model.</p><div class=\"w-richtext\"><figure style=\"max-width:1432px\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/25a0ed6f.png\"/></div></figure><p>‍</p></div><p class=\"paragraph-14\">A quick proof of concept confirmed it worked end to end. Then came the real data.</p><h3 class=\"heading-16\">Before | What we had</h3><p class=\"paragraph-14\">The old architecture had a clear lineage:</p><p class=\"spaced-p\">Data sources (APIs, flat files, SharePoint exports) → Notebooks → Processed tables in the Lakehouse → SQL Analytics Endpoint → Semantic model in import mode → Reports</p><div class=\"w-richtext\"><figure style=\"max-width:1150pxpx\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/e638b1c2.png\"/></div><figcaption>Old architecture diagram</figcaption></figure></div><p class=\"paragraph-14\">The notebooks handled ingestion and processing together because that was the most practical approach when the project was smaller. The import mode semantic model was the standard approach before Direct Lake became a realistic option. The transformation logic spread across notebooks, Power Query and DAX because each layer was solving a real problem at the moment it was introduced.</p><p class=\"paragraph-29\">It worked. The platform delivered real value for real users over a meaningful period. But our needs changed and grew in ambition. We needed live data, tighter governance and room to scale reporting without the complexity multiplying.</p><div class=\"w-layout-grid\"><p class=\"paragraph-26\"><strong>Before</strong></p><p class=\"paragraph-27\"><strong>After</strong></p><p>Single lakehouse layer, no raw history<br/><br/>Credentials hardcoded per notebook<br/><br/>Mixed trigger strategy (scheduled + manual)<br/><br/>Import mode via SQL Analytics Endpoint<br/><br/>Transformation logic split across notebooks, Power Query and DAX<br/><br/>No data recovery path for some data sources</p><p>Bronze / Silver / Gold separation<br/><br/>Centralised credentials via Fabric Environment<br/><br/>Fully scheduled, orchestrated pipelines<br/><br/>Direct Lake connection, no import refresh<br/><br/>All transformation logic in SQL stored procedures<br/><br/><br/>Full raw history in bronze for reprocessing</p></div><h3 class=\"heading-16\">The new architecture | What we built</h3><p class=\"paragraph-29\">The first thing rebuilt was the ingestion layer. New notebooks were written from scratch for all API-based data sources, with a focus on clean separation of concerns: notebooks only fetch and store raw data. Whatever the API returns lands in a delta table with a timestamp recording exactly when it arrived. </p><p class=\"paragraph-29\">Credentials were moved out of individual notebooks entirely and into a Fabric Environment. One centralized location, referenced by all notebooks, never hardcoded anywhere. A small change with a big impact on maintainability and security. The rule for notebooks: use them only where a SQL stored procedure wouldn&#x27;t be enough. That kept the notebook count small and the responsibilities clear.</p><h4>Silver: stored procedures and incremental loads</h4><p class=\"paragraph-29\">With raw data timestamped in bronze, the silver layer could be built to take full advantage of it. For smaller tables, a full truncate and re-insert on every run was clean and simple. For larger tables or tables expected to grow quickly, an incremental pattern using the bronze timestamp avoids scanning the entire source table on every execution:</p><p class=\"paragraph-30\">-- T-SQL incremental upsert pattern --<br/>DECLARE @last_timestamp DATETIME2 = (<br/>  SELECT ISNULL(MAX([timestamp]), &#x27;2020-01-01&#x27;)<br/>  FROM warehouse_dev.silver.target_table<br/>  );<br/>MERGE warehouse_dev.silver.target_table AS target<br/>  USING (<br/>  SELECT * FROM lakehouse_dev.bronze.source_table<br/>  WHERE [timestamp] &gt; @last_timestamp<br/>  ) AS source<br/>  ON target.id = source.id<br/>  WHEN MATCHED AND source.[timestamp] &gt; target.[timestamp]<br/>  THEN UPDATE SET ...<br/>  WHEN NOT MATCHED BY TARGET</p><p>The pattern is simple: check the latest timestamp already in the silver table, then only bring in bronze rows newer than that. The silver layer stays current without touching data that hasn&#x27;t changed.</p><p>Once tables were populated, validation views were created using OneLake shortcuts to the old production workspace, bringing slices of the legacy tables into the dev environment and comparing them row by row against the newly built silver tables. For the major tables, the results matched. For a few edge cases, the bronze layer made it straightforward to trace back, fix the stored procedure logic and reprocess.</p><h4>Gold: Direct Lake semantic model</h4><p>With silver tables clean and validated, the semantic model was rebuilt. The approach was to use a direct lake based semantic model for live data. The key constraint of direct lake mode shapes the entire approach: no calculated columns, no Power Query transformations, no calculated tables. Everything that the model needs must already exist as a column in the silver layer. </p><p>All measures were recreated in DAX, tables were related and reports were rebound to the new workspace. Some visuals needed minor adjustments: column names, formatting, a few measures that behaved slightly differently under direct lake. Everything was traced back and fixed. The end result was a semantic model and report set that behaved identically to the old one, built on a foundation that was orders of magnitude cleaner.</p><div class=\"w-richtext\"><figure style=\"max-width:1488pxpx\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/549b14f5.png\"/></div><figcaption>New architecture diagram</figcaption></figure></div><h3 class=\"heading-16\">Takeaway | Where does the decision belong?</h3><p>The biggest architectural insight isn&#x27;t a technical one: <em>it&#x27;s about where decisions belong</em>. Every transformation that happens inside Power Query, as a DAX calculated column or as a report-level filter is a decision that was deferred past its natural home. The medallion pattern forces those decisions earlier, into SQL, where they can be versioned, tested and reused by anything downstream. </p><p>Preserving raw data in bronze costs almost nothing in a cloud lakehouse in comparison with the benefits it gives. The ability to reprocess from scratch (without calling an API again, without finding the original file) is worth far more than the storage it occupies. </p><p>And that was just the foundation. A clean architecture doesn&#x27;t solve governance by itself. Who controls what gets promoted to production, when and under what conditions: <em>that&#x27;s where the real story continues</em>.</p><h2 class=\"heading-17\">2. Two environments, one source of truth: dev, prod and everything in between</h2><p>Let&#x27;s set the scene. You&#x27;ve just finished rebuilding the medallion architecture in your development environment. Bronze is humming, silver stored procedures are running clean, the semantic model is connected via direct lake, reports look exactly as they should. You&#x27;re happy. You close your laptop.</p><p>The next morning a colleague opens a report and mentions something looks off. You investigate. Turns out a notebook was tweaked, a stored procedure was edited, a table schema shifted slightly and none of it was intentional for production. It just... happened. Because there was only one environment.</p><p>That&#x27;s the part nobody tells you when they hand you the &quot;medallion architecture&quot; keyword list. The layers are important. But so is the question of <em>where</em> those layers live and <em>who</em> can touch them.</p><h3 class=\"heading-16\">The problem | Why one environment isn&#x27;t enough?</h3><p>In the old architecture, there was one lakehouse. Everyone worked in it. Notebooks were edited live. Maybe - <em>maybe</em> - as a better practice you would save a backup just in case. But if not, then if something broke during a run, it broke for everyone. If you were experimenting with a new ingestion approach or rewriting a transformation, that experiment was happening on the same tables the reports were reading from.This is fine when a project is small. It stops being fine the moment more than one person is touching the codebase or the moment you have a client who expects the dashboard to be correct at 9am on a Monday.</p><p>The medallion architecture gave us clean layers. The dev/prod separation gave us a clean boundary around <em>all</em> of them.</p><div class=\"w-layout-grid\"><p class=\"paragraph-26\"><strong>Dev workspace</strong></p><p class=\"paragraph-27\"><strong>Prod workspace</strong></p><p class=\"paragraph-32\">Where all development and testing happens<br/><br/>Notebooks, stored procedures, schema changes — all here first<br/><br/>Direct Lake semantic model built and validated here<br/><br/>Teams failure alerts on bronze and silver pipelines<br/><br/>Pipelines run on a schedule, but changes are safe to experiment with</p><p class=\"paragraph-31\">Receives only what has been validated in dev<br/><br/>No direct editing — all changes flow through the sync pipeline<br/><br/>Semantic model and reports deployed via deployment notebooks (<em>stay tuned</em>)<br/><br/>Teams failure alerts on all prod pipelines<br/><br/>Sync can be paused manually or flipped automatically via trigger</p></div><p class=\"paragraph-33\">The rule is simple: nothing goes to production manually. Everything flows through a controlled sync.</p><h3 class=\"heading-16\">The build | The sync pipeline</h3><p>The core idea behind the sync is straightforward. Dev and prod warehouses share the same schema. When a pipeline run completes successfully in dev, the sync pipeline copies the resulting silver tables from dev into prod table by table, in a controlled sequence.</p><p>Under the hood, the sync uses a <em>Lookup</em> activity that builds a dynamic list of tables to sync, followed by a <em>ForEach</em> that iterates through them sequentially. Each iteration runs a <em>Copy</em> activity with a truncate-and-insert strategy: the prod table is cleared, then repopulated from dev. No partial states, no row-level merging between environments, just a clean, deterministic copy.</p><p><em>Why truncate and insert, not merge? Because the silver tables in dev are already in the validated state. There&#x27;s no reason to be surgical about what goes to prod: if dev is good, prod should look exactly like dev. Truncate and insert makes that guarantee explicit. &quot;But what if dev isn&#x27;t good?&quot; - that&#x27;s also covered and we&#x27;ll get to it.</em></p><p><em class=\"italic-text-2\">Each of the caller pipelines: Daily Data, Weekly Data and Manual Data invokes the master sync pipeline after its own run completes. The caller runs its notebooks and stored procedures, verifies success, then hands off to the sync. Each caller pipeline runs independently from the others, ingesting only the tables specific to itself and respecting its own schedule. Failure at any point in a caller pipeline triggers a Teams alert and stops execution before the sync is ever reached.</em></p><p>Why independent caller pipelines? It makes no sense to always pull the entire silver layer data volume from dev to prod. Each pipeline only syncs what it owns, based on its own schedule: Daily data runs multiple times a day, Weekly data once a week, Manual data on demand.</p><div class=\"w-richtext\"><figure style=\"max-width:1343px\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/07afb8c1.png\"/></div></figure><p>‍</p></div><h3 class=\"heading-16\">The pause gate</h3><p>Having a sync pipeline is useful. Having a way to <em>stop</em> it without touching any pipeline configuration is essential.</p><p>There&#x27;s a table in the prod warehouse called <strong>sync_control</strong>. It has one column that matters: <strong>pause_sync</strong>, a single bit flag. Before the master sync pipeline runs any copy activity, it checks this flag. If it&#x27;s set to <strong>1</strong>, the sync stops, meaning our trigger detected an anomaly or someone intentionally paused it. Nothing is written to prod, no error reaches the semantic model or report level. Because we also got an alert, we can now check what&#x27;s wrong at dev level and fix the problem while prod continues working fine.</p><p>But what if you simply want to pause the sync because you have planned work to do? Toggling the flag is done through a separate, single-activity pipeline (let’s call it <em>Set Sync State</em>): a Script activity that flips the bit. No UI changes, no pipeline edits, no credentials required beyond the workspace access you already have. One pipeline run to pause, one to resume. <strong>0</strong> means <strong>sync is active</strong>, <strong>1</strong> means it&#x27;s <strong>paused</strong>.</p><p class=\"paragraph-30\">-- T-SQL sync control table -- <br/>CREATE TABLE warehouse_prod.silver.sync_control (pause_sync BIT NOT NULL DEFAULT 0);</p><p>Why does this matter in practice? You&#x27;ve just discovered an issue in a stored procedure that&#x27;s producing incorrect output for one table. The dev pipelines are still running on their schedule. Without the pause gate, every run would push that incorrect data straight to prod. With it, you flip the flag, fix the procedure, validate in dev, then resume the sync when you&#x27;re confident.</p><h3 class=\"heading-16\">The automation</h3><p>Manually flipping the sync flag is useful. But having it flip <em>itself</em> when something goes wrong is even better.</p><p>In the dev workspace, a data quality snapshot table is populated on every pipeline run. A Power BI report built on top of it contains a measure that evaluates whether any key metric has shifted beyond an acceptable threshold between the latest snapshot and the one from the previous run. If the rule breaks, say, the number of orders drops by more than x% overnight, then an <em>Activator</em> alert fires.</p><p>Below is a real trigger in action. At 09:54, the sync is running normally: <strong>pause_sync = 0</strong>. At 09:57, the Activator detects a change in the data quality measure and fires, calling the<strong> Sync ON/OFF</strong> pipeline with <strong>pause_sync = true</strong>. By 10:00, the table reflects the new state: <strong>pause_sync = 1</strong>. Three minutes from breach detection to sync paused, fully automated, no manual intervention required.</p><p>The Activator rule runs every 15 minutes, scheduled in between the bronze ingestion notebooks. That gap is deliberate and it gives the Activator time to evaluate the latest data and pause the sync before the next fetch runs. If a breach is detected, the gate closes before new data reaches production.</p><div class=\"w-richtext\"><figure style=\"max-width:1432pxpx\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/aaf0d27b.png\"/></div><figcaption>1. Sync is active, data flows from dev to prod</figcaption></figure><p>‍</p></div><div class=\"w-richtext\"><figure style=\"max-width:975pxpx\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/f4a19f63.png\"/></div><figcaption>2. The activator fires, the data quality metric value changed, the rule triggered and the Sync ON/OFF pipeline was called with pause_sync = true</figcaption></figure></div><div class=\"w-richtext\"><figure style=\"max-width:1429pxpx\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/c025509b.png\"/></div><figcaption>3. Sync state is inactive, pause_sync has been updated</figcaption></figure><p>‍</p></div><p>That Activator alert does two things simultaneously: it sends a notification to a Teams channel so the right people are informed immediately and it triggers the <em>Set Sync State</em> pipeline, automatically flipping pause_sync to 1. The sync stops. Prod is protected. The team has time to investigate in dev without any bad data propagating downstream.Here&#x27;s how the full flow looks end to end: from a dev pipeline run all the way through to prod reports, with the automated gate sitting across the boundary:</p><div class=\"w-richtext\"><figure style=\"max-width:852px\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/57f1b9c7.png\"/></div></figure><p>‍</p></div><h3 class=\"heading-16\">Takeaway | What does the separation actually give you?</h3><p>Dev/prod separation sounds like obvious engineering best practice. And it is. But in a Microsoft Fabric context, where the boundaries between development and production can get blurry very fast: same capacity, same tenant, easy to just edit something live, it requires deliberate architecture to enforce it.</p><p>The sync pipeline makes promotion from dev to prod a conscious, traceable act. The pause gate makes it reversible and controllable without requiring anyone to touch pipeline configuration under pressure. The automated trigger closes the last gap: even if nobody is watching, the gate closes itself when the data says something is wrong.</p><p>The sync gate exists precisely because of how Direct Lake works. Every change that reaches the gold layer is immediately visible in all reports, including embedded ones served to clients. There&#x27;s no refresh buffer, no scheduled window, no lag between a data push and what a client sees on screen. When data updates, reports update.</p><p>That&#x27;s the power of Direct Lake. It&#x27;s also the risk. A bad data push doesn&#x27;t sit in a queue waiting for the next scheduled refresh, it reaches your clients in real time. The sync gate is the only thing standing between a processing error and a client-facing report.</p><p>The medallion architecture gave the data clean layers. The dev/prod separation gave the team clean control over when those layers go live.</p><h2 class=\"heading-17\">3. What the numbers say: reading Fabric Capacity Metrics before and after</h2><p><em>Most people open the Capacity Metrics dashboard when something is on fire. We opened it before and after a full architecture migration and the comparison showed us why the rewrite was worth it.</em></p><p>There&#x27;s a dashboard in Microsoft Fabric called Capacity Metrics. It lives behind a separate <a href=\"https://learn.microsoft.com/en-us/fabric/enterprise/metrics-app\"><strong>app installation</strong></a> and the first time you open it you&#x27;ll spend about ten minutes wondering whether the numbers are good or bad. There&#x27;s no green zone, no red line: just bars and CU seconds and a gentle reminder that you are responsible for your own interpretation. <strong>CU</strong> stands for <strong>Capacity Unit</strong>. It&#x27;s the currency Fabric charges for compute. Every notebook run, every stored procedure execution, every semantic model refresh, every pipeline activity. All of it gets converted into CU seconds and tallied up. </p><p>We had both architectures running on the same Fabric capacity during the migration window, which gave us something rare: a direct side-by-side comparison over the same days period. Worth noting upfront: both workloads were active simultaneously, so the numbers aren&#x27;t perfectly isolated. But the patterns are clear enough to be meaningful.</p><h3 class=\"heading-16\">A quick primer | What is a CU, actually?</h3><p>Before looking at numbers, it&#x27;s worth understanding what you&#x27;re measuring. The dashboard shows CU (s) everywhere and the unit is easy to misread.</p><p><em>CU (s) = Capacity Unit-seconds (think it as compute intensity × duration, combined into one number)</em></p><p class=\"spaced-p\"><strong>CU is not &quot;seconds&quot; </strong>The (s) is the time dimension. A CU measures how much compute resource was consumed; the (s) tracks how long that consumption lasted. Together they give you total computational cost.<br/><br/>‍<strong>Think: kilowatt-hours</strong> Just like electricity bills combine wattage × time, CU (s) combines compute intensity × duration. A heavy query that runs briefly can cost the same as a lighter query that runs longer.<br/><br/>‍<strong>What it measures</strong> Every notebook run, every stored procedure execution, every semantic model refresh, every pipeline activity - all of it converted into CU seconds and tallied up per workspace, per item, per day.</p><p class=\"paragraph-34\"><em>The dashboard lets you slice this by workspace, by item kind, by day and by individual item. Once you understand what you&#x27;re looking at, it becomes a very honest mirror of your architecture&#x27;s efficiency.</em></p><h3 class=\"heading-16\">The headline | 42% fewer CUs for equivalent work</h3><p>At workspace level, the old architecture consumed 472,492 CU seconds across its three workspaces over 14 days. The new architecture consumed 272,200 CU seconds across its two. That&#x27;s a reduction of roughly 42% for a platform that handles the same data sources, produces the same reports and serves the same users.</p><p>The image below shows the workspace-level breakdown as it appears in the Capacity Metrics app. The old architecture workspaces: Data (lakehouse, notebooks), Internal  (internal semantic models, reports) and External (external semantic models, reports). The new architecture Dev and Prod workspaces aside. Same capacity, same period, same data.</p><div class=\"w-richtext\"><figure style=\"max-width:1321pxpx\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/a340b09d.png\"/></div><figcaption>Source: MS Fabric Capacity Metrics</figcaption></figure></div><h3 class=\"heading-16\">The breakdown | Where the CUs actually went</h3><p>The aggregate number is satisfying, but the per-item breakdown is where the architectural story becomes visible. Here are the top consumers across both architectures:</p><div class=\"w-richtext\"><figure style=\"max-width:1413pxpx\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/cb36d681.png\"/></div><figcaption>Source: MS Fabric Capacity Metrics</figcaption></figure></div><p><strong>Two numbers</strong> jump out immediately:</p><h4>The notebook problem</h4><p>In the old architecture, notebooks consumed <strong>203,093 CU seconds</strong> - <strong>more than 43% of everything the old platform used in two weeks</strong>. This was the notebook doing all the work: reading from APIs, filtering, deduplicating, transforming, aggregating and writing back to the lakehouse. Notebooks doing most of the heavy work, paying CU every time they ran. And they ran a lot.</p><p>In the new architecture, the <strong>notebooks consumption dropped to 37,570 CU seconds</strong>. The notebooks now only do what notebooks are genuinely needed for: bronze ingestion from external APIs. Everything else moved to SQL stored procedures in the warehouse. And warehouse compute, it turns out, is considerably cheaper per operation than notebook compute for structured transformation work.</p><div class=\"w-richtext\"><figure style=\"max-width:1022px\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/702ef290.png\"/></div><figcaption>Old vs New Architecture CU (s) consumption</figcaption></figure></div><h4>The semantic model problem</h4><p>The second number is the old architecture&#x27;s cost: <strong>188,583 CU seconds</strong>. This was the import-mode semantic model doing what import-mode semantic models do: running full scheduled refreshes, loading all the data from the SQL Analytics Endpoint into memory, over and over, on a fixed schedule.</p><p>In the new architecture, the equivalent dataset items consumed <strong>14,284 CU seconds in dev</strong> and <strong>1,640 CU seconds in prod</strong> (<strong>17,341 total</strong>). The reason is Direct Lake: when the semantic model connects directly to the Delta tables in the warehouse, there is no refresh to run. The model reads live data at query time. The massive CU cost of repeated full imports simply disappears. We will talk about Direct Lake connections in the future chapter (<em>*stay tuned*</em>).</p><div class=\"w-richtext\"><figure style=\"max-width:1014px\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/21575df5.png\"/></div><figcaption>Old vs New Architecture CU (s) consumption</figcaption></figure><p>‍</p></div><h3 class=\"heading-16\">Takeaway | What the metrics measure?</h3><p>Capacity Metrics won&#x27;t tell you your architecture is good or bad. It will show you exactly what you&#x27;re paying for in compute and if you know what you&#x27;re looking at, that&#x27;s often enough.</p><p>In our case, two line items explained most of the cost difference: notebooks doing transformation work they shouldn&#x27;t have been doing and a semantic model refreshing data it could have been reading directly. Fix those two things if you can: move transformations to SQL, move the semantic model to Direct Lake. The savings follow naturally. </p><h2 class=\"heading-17\">4. How data reaches Power BI: import mode vs Direct Lake</h2><p><em>Different ways to connect a semantic model to its data source. One of them changed everything about how our platform performs and what the model has to carry in memory.</em></p><p>When you build a semantic model in Power BI or Microsoft Fabric, one of the first decisions you make, often without realizing it, is how the model connects to its data. This choice shapes everything downstream: query performance, refresh costs, memory footprint and how fresh the data actually is when a user opens a report.</p><p>There are three connection modes. Most people start with one (usually import mode) and never revisit the decision. We did, and the difference was significant enough to dedicate a chapter to it.</p><p>Here is how each connection types work:</p><div class=\"w-layout-grid grid-4\"><p class=\"paragraph-37\"><strong>Import model (Classic)</strong></p><p class=\"paragraph-38\"><strong class=\"bold-text-13\">DirectQuery (Live)</strong></p><p class=\"paragraph-39\"><strong>Direct Lake (Fabric-native)</strong></p><p class=\"paragraph-36\">Data is copied into the model&#x27;s in-memory store on refresh<br/><br/>Queries run against the in-memory copy, fast<br/><br/>Data is only as fresh as the last refresh<br/><br/>Full refresh required to see new data<br/><br/>Model size grows with data volume<br/><br/>High CU cost per refresh cycle</p><p class=\"paragraph-36\">No data stored in the model - queries go straight to the source<br/><br/>Always live, always fresh<br/><br/><br/>Performance depends entirely on source query speed<br/><br/>No refresh cost, but every visual fires a query<br/><br/>DAX → SQL translation overhead on every interaction<br/><br/>Limited DAX and modelling support</p><p class=\"paragraph-36\">Reads directly from Delta Parquet files in OneLake<br/><br/>No data copied, no refresh scheduled<br/><br/>Near-import query speed via column streaming<br/><br/>Data updates as soon as the Delta table updates<br/><br/>Zero model memory footprint<br/><br/><br/>Requires Fabric - not available in classic Power BI</p></div><p class=\"paragraph-41\">DirectQuery is an obvious answer to import mode&#x27;s staleness problem, but it trades away query performance and DAX flexibility, which makes it impractical for complex models with many measures and calculated logic. Direct Lake is the Fabric-native answer that avoids that trade-off: near-import speed, without any in-memory copy, without a refresh cycle.</p><p>For our use case - a warehouse with well-structured silver tables, complex DAX measures and a need for data that&#x27;s current within the last pipeline run - Direct Lake was the right call.</p><h3 class=\"heading-16\">A common question | Does a Fabric Warehouse look like Delta to Direct Lake?</h3><p>Yes! And this is worth understanding properly, because it&#x27;s not obvious.</p><p>A Fabric Warehouse exposes a T-SQL interface, so it feels like a traditional SQL database. But under the hood, every table created in a Fabric Warehouse is physically stored as a <a href=\"https://learn.microsoft.com/en-us/fabric/data-warehouse/architecture\"><strong>Delta Parquet table in OneLake</strong></a>, the same format used by Lakehouse tables. You can browse to it directly via the OneLake file explorer and see the Parquet files and Delta log sitting there.</p><p>Direct Lake doesn&#x27;t connect to the Warehouse as an SQL engine, it connects to the Delta files the Warehouse writes to OneLake. The T-SQL interface and the Direct Lake connection are two different ways of reading the same underlying files. This is why our semantic model can connect via Direct Lake to warehouse tables even though we interact with those tables via stored procedures and T-SQL.</p><p>The practical implication: when a stored procedure runs and upserts rows into a warehouse table, it updates the Delta files in OneLake. The semantic model&#x27;s Direct Lake connection sees those updated files immediately - no refresh required, no intermediate step. The pipeline run is the &quot;refresh.&quot;</p><h3 class=\"heading-16\">Semantic Models | Before and after</h3><p>Here&#x27;s how the data path looked in the old architecture and how it looks now:</p><p><strong>Old architecture </strong>- data copied into memory on every scheduled refresh - model = 96.90 MB - 81 tables - 700 columns</p><div class=\"w-richtext\"><figure style=\"max-width:1432px\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/bb653701.png\"/></div></figure></div><p><strong>New architecture </strong>- no refresh - data live after each pipeline run - model memory = 0 B - 43 tables - 441 columns</p><div class=\"w-richtext\"><figure style=\"max-width:1432px\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/21869d94.png\"/></div></figure></div><h3 class=\"heading-16\">What the Vertipaq Analyzer showed</h3><p>The Vertipaq (Memory) Analyzer connects to a semantic model and reports exactly what it&#x27;s holding in memory table by table, column by column. Running it against both models produced the starkest numbers in this entire article.</p><div class=\"w-richtext\"><figure style=\"max-width:1600px\" class=\"w-richtext-align-fullwidth w-richtext-figure-type-image\"><div><img alt=\"Article content\" src=\"./images/72909b71.png\"/></div></figure></div><p>The old model&#x27;s heaviest tables were the main fact tables, each occupying between 17 MB and 23 MB individually, with two auto-generated LocalDateTable calculated tables consuming another 24 MB between them. Not because it has no data (the same tables exist, with the same rows), but because Direct Lake doesn&#x27;t load anything into the model. It reads column segments from the Delta Parquet files in OneLake on demand, at query time, without ever holding a full in-memory copy.</p><p>The model also got smaller structurally during the rewrite. Going from 81 tables and 700 columns to 43 tables and 441 columns reflects the cleanup that happened when the new silver layer was built: intermediate tables that existed only because Power Query needed them, calculated tables that compensated for missing columns in the source and duplicated date tables that the auto-date feature had generated silently over time - all of it removed, because the silver stored procedures now handle that logic before data ever reaches the model.</p><h2 class=\"heading-17\">Final thoughts</h2><p>Hopefully, this article gave you some ideas for evaluating an existing or a new Fabric architecture you&#x27;re building.</p><p>It&#x27;s important to assess what you&#x27;re trying to solve and what your users need before choosing the right methodology for your use case.
